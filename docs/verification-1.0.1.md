## 上轮审查问题与本轮结果

| 问题 | 修正与证据 |
| --- | --- |
| 孤立弯轨使单线普通铁路误成路 | 弯道两条线路的两个方向都须连续接上激活动力双轨；新增伪造弯道、缺失第二侧和区块边界回归测试。 |
| 客户端道路几何被丢弃、没有站点上传 | 实际上传候选参与逐段重建校验；GameTest 经真实 Fabric 网络处理器验证伪造／合法道路数据。站点上传须通过服务端提供者授权及线上位置校验，并强制保护标记。 |
| 全局施工阻止无关 TP | 仅刷新相关连通几何的待处理修改；真实 TP_QUERY／TP_REPLY 往返测试在无关施工和全局版本改变后仍完成传送。 |
| 配置重载保留旧宽度道路 | 检测规则改变时先使旧自动数据失效，再分批重建已加载区块；测试证明最小冰路宽度 3→5 后旧三格道路移除，API 道路保留。 |
| 门被当成单点、已有门发现有盲区 | 保存真实矩形门面，区块扫描提交实际门方块。GameTest 覆盖宽门远端连接、网格边界已有门、激活／破坏／出口改配对。 |
| 严格跨维度站点受 ID 排序影响 | 保留“最近目标区域”主规则，平局时比较经过可达传送门的分维度几何距离；覆盖改名不改变优选落点及多个传送门。 |
| 朝向丢失、落点被隐式调整 | 保留原版显式目标命令的 yaw/pitch 与 facing；真实往返验证。safeLanding 默认 false，保留图的精确坐标；启用时连续检查配置范围内高度。 |
| 全量网络／数据库开销 | GZIP 全量与版本增量、后台编码、后台 SQLite 合并保存。稀疏排序号避免删除首条道路后重写后续道路；触发器测试禁止修改未变道路及顶点。 |
| 客户端缓存只写不读 | 读取缓存作为同步基线；只有本次连接的新鲜服务端数据才能启用计算，错误增量请求全量恢复。 |
| 修改后立即卸载可能保留旧道路 | 服务端已确认的修改会使无法复核的受影响自动段失效；纯客户端未加载提示不授权删除。两项实际区块卸载测试覆盖自身及相邻平行线区块，并检查 API 数据保留。 |

## 明确的设计与验证边界

- 城市仍按 X/Z 多边形计算，不设置城市高度范围。
- 严格模式的平局比较采用“同维度直线距离之和，穿越配对门代价为 0”的几何距离；不宣称这是沿铁路行驶的里程。
- 同步协议 v2 要求客户端、服务端同时升级；已有 SQLite v1 数据迁移到 v2，旧版程序不能读取新版数据库。
- 客户端提案只是候选；服务端还会合并执行后台完整性扫描，补足空提案、不完整区块或分批上传遗漏的新道路。
- 一万条短道路样本的编码大小检查约为全量 87 KB、单条修改增量 439 字节；这不是服务器 TPS 或并发容量测试。
- GameTest 使用真实 Minecraft/Fabric 网络处理器与内存 Netty 连接，覆盖序列化请求、客户端等价图计算和序列化响应。尚未进行两台实际游戏客户端的 GUI 联机验收，也未完成大服压力测试。
