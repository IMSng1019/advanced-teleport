# ATP · Advanced Teleport

面向 **Minecraft Java 1.20.4 / Fabric** 的城市与交通网络传送模组。普通玩家的 `/tp`、`/teleport` 会根据城市、铁路、蓝冰道路、站点和传送门计算允许到达的位置；权限等级 **2 及以上** 的管理员保留原版传送。

客户端检测道路变化并计算传送候选位置，服务端根据实际方块和权威路网再次验证。客户端缓存不能自行决定服务端的道路或传送结果。

## 安装与构建

1. 客户端和服务端均安装 Minecraft 1.20.4、Fabric Loader 0.16.10 或更高兼容版本，以及适用于 1.20.4 的 Fabric API。项目使用 Fabric API `0.97.3+1.20.4` 构建。
2. 将 `advanced_teleport-1.0.1.jar` 放入两端的 `mods` 文件夹。不要安装 `-sources.jar`。客户端和服务端应使用相同 ATP 版本；1.0.1 的同步协议 v2 与 1.0.0 不兼容。
3. 游戏运行需要 Java 17 或以上。SQLite JDBC 已嵌入 ATP JAR；**Fabric API 仍需单独安装**。

从源码构建时使用 **JDK 21** 运行 Gradle；生成的模组字节码目标版本为 Java 17：

```powershell
.\gradlew.bat test build
```

Linux/macOS：

```sh
./gradlew test build
```

产物位于 `build/libs/`。单元测试覆盖几何、连通图、道路检测、数据保护、数据库与同步分片等行为；实际多人游戏仍应按下方清单验证。

使用 Fabric 官方无界面 GameTest 服务器验证实际 Minecraft 事件、Mixin、命令权限及 SQLite 持久化：

```powershell
.\gradlew.bat runGametest
```

测试世界位于 `build/gametest/`，报告为 `build/gametest-results.xml`；测试模组不包含在正式 JAR 中。测试工程也包含真实 Minecraft/Fabric 网络处理器与 Netty 内存连接的请求／响应检查。它们不能替代两台游戏客户端的 GUI 联机验收或大规模负载测试；结果以本次运行生成的报告为准。

## 数据目录

正常安装时，以 ATP JAR 所在的 `mods` 为基准，数据根目录是 **`../advanced_teleport`**：

```text
游戏或服务端目录/
├─ mods/
│  └─ advanced_teleport-1.0.1.jar
└─ advanced_teleport/
   ├─ config.json
   └─ 地址端口+世界名称-身份哈希/
      └─ graph.sqlite
```

目录不存在时会创建，已有数据会读取。世界身份使用实际存档相对于默认存档根目录的完整路径（服务端为运行目录，单机为运行目录下的 `saves`），避免显示名相同或嵌套目录末级同名的存档串档。例如 `season1/world` 与 `season2/world` 使用不同数据库，普通 `world` 或单机 `saves/新的世界` 的原有数据目录保持兼容。地址、端口、世界身份会转换为 Windows 等平台可用的名称，并添加稳定哈希，避免 IPv6、特殊字符或截断名称造成串档。单机使用 `singleplayer` 地址标识；开发环境以 Fabric 游戏运行目录为基准。不同维度保存在同一个世界数据库中，并分别记录维度 ID。

自定义 `--universe` 的路径也参与世界身份；跨磁盘存档使用完整绝对路径，因此这类存档更换磁盘或路径时数据目录会改变。同步世界身份上限为 1024 字符。旧版可能已混用的嵌套世界数据库会保留，但不会自动归给任何一个新目录；需要保留其中的注册数据时，应先备份并确认归属，再迁入对应世界的数据目录。

服务器的 `graph.sqlite` 是权威数据；客户端按连接的服务器地址与世界名称读取并保存 `client-cache.sqlite` 同步缓存。加入服务器收到 GZIP 压缩的完整图，后续更新通常只传输新增、修改和删除的记录。增量版本不匹配时，客户端请求重新下发完整图。

客户端读取的缓存可以用于恢复同步基线，但收到本次连接的新鲜服务端数据之前不会启用 TP 计算。每次传送仍由服务端复算，修改客户端缓存不能改变服务器允许的落点。

1.0.1 会将已有 SQLite v1 数据库迁移到 v2，保留记录并补充传送门面范围。运行期间使用事务增量写入，后台线程合并待保存版本；正常停服会等待最新版本写完。备份时建议正常停服后复制整个 `advanced_teleport` 目录。无法读取的配置或数据库会报告错误，不会静默清空重建。

编码大小检查中，一万条短道路段的压缩完整图约为 87 KB，修改一条道路后的增量为 439 字节。该结果只说明此数据样本的传输大小，不代表服务器 TPS 或并发容量。

## 传送模式

| 模式 | 普通玩家起点条件 | 实际落点 |
| --- | --- | --- |
| `default` | 位于城市内或允许接近的道路范围内 | 自己可达的区域中，距请求目标最近的点 |
| `strict` | 靠近已注册且有效的站点 | 自己的连通网络中，距目标所属区域最近的站点 |
| `off` | 使用原版命令权限 | 原版 TP |

`defaut` 作为 `default` 的兼容拼写也可读取。启用限制时，普通玩家只能传送自己；不能借此传送其他玩家或实体。关闭限制后恢复原版权限，因此没有原版 TP 权限的普通玩家不能仅凭 ATP 使用原版 `/tp`。

严格模式要求目标也处于已知城市或道路范围。它选择的是**出发网络中的站点**。目标网络与出发网络可以不连通；在能进行同维度距离比较时，首先选择最接近目标网络的出发站点。

若站点到目标网络的距离相同，则比较到请求目标的最短传送门路线：同一维度内累计直线距离，跨越一对传送门的代价为 0。该度量不是沿铁路折线行驶的里程。路线距离也相同时，按位置及稳定 ID 决定，避免仅改名就改变不同距离站点的优先级。

跨维度不直接比较两组坐标。默认模式只寻找目标维度中已经与起点连通的区域；没有连接到该维度时拒绝传送。默认 `safeLanding=false`，保留图选中的精确坐标。管理员启用 `safeLanding` 后才会检查碰撞、流体和落脚空间，并在配置的垂直范围内寻找可达安全位置；找不到则取消。

## 城市、道路、站点与传送门

- **城市**：同一维度内的闭合 X/Z 多边形，沿高度方向视为城市范围。城市可以通过管理员选点命令或 API 注册。两个城市重叠或接触，不会仅因此自动连通。
- **铁路**：直线部分识别两条同向、已激活的动力铁轨，默认中间隔 1 格。普通铁轨弯道需要成对、连续的接近段，并连接有效的双线动力铁轨；两块孤立弯轨不能让旁边的单线普通铁轨取得道路资格。弯道间隔按水平曼哈顿距离减 1 计算。
- **蓝冰道路**：默认宽 3–5 格，道路两侧在冰面方块 Y+1 处有实体护栏，并保留通行净空。支持直路、直角转弯及同宽 T 型、十字路口；路口中心需要完整蓝冰地面和两格净空，各侧必须是完整护栏或有护栏的同宽支路。任意散铺蓝冰不会直接组成道路。
- **站点**：必须位于已知道路折线上，注册允许 0.1 格浮点误差。ATP 不自动创建站点，交由其他模组调用 [注册 API](docs/API.md)。客户端可以提交站点，但服务端必须先注册对应处理器，核验权限、设施归属与实际方块。
- **道路连接**：道路穿过城市或部分位于城市内，即与该城市连接；两条道路的三维线段距离满足配置，即互相连接。连接可传递，但跨不同维度的道路不会直接按坐标相近而连接。
- **传送门连接**：按道路到完整门面的距离连接，宽门不再只比较左下角。区块加载会按实际门方块发现已有门。下界门激活或附近道路更新时，通过原版查找规则匹配现有出口；实际穿门会确认两端。新出口改变原版配对时，过时的自动连接会被复核。另一端尚不存在时不凭空创建出口。普通 `/tp` 跨维度不会被当作新门连接。

铁轨放置、拆除、形状或供电改变，蓝冰及护栏变化，以及传送门状态变化，会触发局部更新。客户端上传实际道路候选，服务端按真实方块验证并使用这些候选。遗漏的候选通过合并后的区块补扫发现；客户端队列满时保留区块恢复任务。局部更新会合并，并按每 tick 的预算处理。

道路检测不会强制加载远处区块；传送门出口查找采用原版 POI 查询。未加载方块不视为空气。TP 会优先核对起点路网及严格模式目标区域相关的待处理变化；与这次行程无关的远处施工不会仅因队列非空就阻塞传送。相关工作超过 `maxTeleportUpdates` 时才要求稍后重试。

已有世界的道路会在相关区块加载、局部变化或管理员 `/atp scan` 时逐步发现。`scan` 仅扫描玩家附近；ATP 不会在启动时遍历整个未加载世界。大型特殊道路、其他模组的道路或不符合自动检测形状的结构，可通过受保护 API 注册。

API 注册的城市、道路、站点与传送门会强制带保护标记。自动检测不能覆盖或删除这些记录。道路消失后，受保护站点仍保留，但在道路恢复且站点重新有效之前不会参与传送；其他模组或管理员可以显式移除注册数据。

## 配置

配置文件位于服务端 `advanced_teleport/config.json`。客户端计算采用服务器下发的配置。修改后执行 `/atp reload`；非法配置会报错，并保留原文件供修正。

铁路间隔或冰路宽度等检测配置改变时，重载会先撤销自动道路，再对已加载区块按新规则重建；尚未加载的区块在之后加载时重新发现。API 注册的受保护数据保留。重建过程中，可达范围可能暂时缩小。

| 字段 | 默认值 | 说明 / 允许范围 |
| --- | --- | --- |
| `mode` | `"default"` | `default`、`strict`、`off`，兼容 `defaut` |
| `roadConnectionDistance` | `2` | 道路间连接距离，0–128 格 |
| `portalConnectionDistance` | `3` | 道路到传送门的连接距离，0–128 格 |
| `roadAccessDistance` | `2` | 玩家离道路多近视为位于路网，0–128 格 |
| `stationAccessDistance` | `3` | 严格模式的站点使用距离，0–128 格 |
| `railStraightGap` | `1` | 平行直线铁轨中间的间隔，0–8 格 |
| `railCornerMinGap` | `2` | 铁轨弯道最小间隔，0–8 格 |
| `railCornerMaxGap` | `3` | 铁轨弯道最大间隔，最小间隔–8 格 |
| `iceMinWidth` | `3` | 蓝冰道路最小宽度，1–9 格 |
| `iceMaxWidth` | `5` | 蓝冰道路最大宽度，最小宽度–9 格 |
| `maxPendingChangesPerTick` | `4` | 每 tick 处理的局部检测队列项，1–256 |
| `clientResponseTimeoutTicks` | `100` | 客户端传送计算响应期限，20–1200 tick；正常 20 TPS 下默认约 5 秒 |
| `maxGraphEntries` | `100000` | 路网容量限制，100–1000000；同步快照另有总字节上限 |
| `safeLanding` | `false` | 是否启用额外安全落点检查；关闭时保留图计算坐标 |
| `safeLandingVerticalRange` | `16` | 开启安全落点后尝试的上下范围，0–64 格 |
| `maxTeleportUpdates` | `32` | 一次 TP 优先处理的相关更新上限，1–256 |

检测范围会随最大道路宽度和弯道间隔扩大，提高参数可能增加计算量。距离参数必须是有限数值。配置文件上限为 64 KiB。

## 命令

| 命令 | 用途 |
| --- | --- |
| `/tp <x> <y> <z>`、`/teleport ...` | 使用当前模式传送自己；管理员保留原版完整命令形式 |
| `/atp tp <dimension> <x> <y> <z>` | 明确指定目标维度，例如 `minecraft:the_nether`；普通玩家仍受当前模式限制 |
| `/atp status` | 查看模式和路网状态 |
| `/atp mode default\|strict\|off` | 管理员修改模式并保存配置 |
| `/atp reload` | 管理员重新读取配置 |
| `/atp sync` | 为当前玩家重新下发路网同步数据 |
| `/atp scan` | 管理员重新扫描当前位置附近 |
| `/atp city begin <id>` | 管理员开始创建城市 |
| `/atp city vertex` | 将当前位置加入城市顶点序列 |
| `/atp city save` | 保存城市；至少需要 3 个同维度顶点，首尾自动闭合 |
| `/atp city cancel` | 放弃正在编辑的城市 |
| `/atp city remove <id>` | 显式删除城市 |
| `/atp city list` | 列出城市 |

创建城市时沿边界依次选点，使用不自交的多边形。城市 ID 不得以 `auto:` 开头，该前缀留给自动发现的基础设施。

朝向参数沿用原版命令语法，例如 `/tp <自己的名字> <x> <y> <z> <yaw> <pitch>` 或显式目标形式的 `facing`。受限传送完成后会应用朝向；ATP 不扩展原版不存在的参数组合。

受限传送按原版流程唤醒睡眠中的玩家、释放原床，并在传送时更新朝向；玩家未使用鞘翅飞行时会清零垂直速度，保留水平速度。鞘翅飞行时保留飞行速度和状态。

## 多人验证清单

以下是交付后的实机验收步骤，不代表已完成多人 GUI 验证。建议使用备份世界、一个权限等级 2 的管理员和两个普通玩家测试：

1. 两端安装 ATP 与 Fabric API 后启动服务器；确认生成配置、当前世界数据库，普通玩家加入后收到路网数据。
2. 创建两个互不连接的城市 A、B。普通玩家在 A 内请求 B 的坐标，应落到 A 中最接近目标的位置；在任何城市/道路外请求 TP 应被拒绝。管理员 TP 应直接到达目标。
3. 仅让两个城市边界重叠，验证未通过重叠建立永久道路连接；再铺设符合规则的铁路连接 A、B，等待同步后验证可达范围扩大。
4. 铁路直线处使用两条同向动力铁轨，中间空 1 格；分别测试通电、断电、拆除与普通铁轨转弯。另一名玩家应收到道路更新，断开的路网应影响后续 TP。
5. 铺设有护栏的 3 格与 5 格宽蓝冰道路、直角弯及同宽 T 型和十字路口，验证各支路互通；测试拆除护栏或冰块后的变化。2 格和 6 格宽道路在默认配置下不应作为有效直路。
6. 用接入 API 的站点模组注册两个站点，切换 `strict`。远离站点请求 TP 应失败；靠近站点时应选择出发连通网络中最接近目标区域的站点。目标在未知区域时应失败。
7. 在传送门两侧铺设连接道路，实际通过一次门建立配对，再使用 `/atp tp` 测试跨维度。删除门后，相关自动连接应失效；另一端尚未加载时不应被当作空气删除。
8. 在计算期间修改无关城市的道路，未受影响的请求应继续；修改实际经过的连接或重载配置时，应重新核对或要求重试。普通玩家不能通过多目标命令传送其他玩家。验证显式目标命令的角度和 `facing`。
9. 退出后重进、正常重启服务器，确认城市、道路、站点与保护标记仍在，客户端旧缓存被服务端快照替换。
10. 切换 `off`：管理员使用原版 TP，普通玩家恢复原版权限限制。切回 `default` 后重新验证普通玩家的自传送。
11. 把冰路最小宽度从 3 改成 5 后重载，旧三格自动道路应失效，受保护 API 道路应保留；再改回并等待已加载区块重建。
12. 使用客户端站点入口提交真实设施；服务端处理器未注册、权限不足、设施方块不存在或归属不符时，应拒绝请求。有效站点应同步到另一名玩家。

其他模组直接调用实体传送方法、床/重生、末影珍珠等不属于 ATP 对原版 TP 命令的拦截范围。API 和自动检测的几何规则见 [docs/API.md](docs/API.md)。
